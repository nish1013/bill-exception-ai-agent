# Decisions

## 2026-10-21 — brief review of `docs/brief.md` at `5ff6e68`

| # | Kind | Decision | Why | Alternatives considered | Consequence |
|---|---|---|---|---|---|
| D1 | product | A duplicate is the same tenant, supplier and normalised invoice number. Same amount and a date within 7 days is a weaker "possible duplicate". | **F1.** The invoice number is the supplier's own key, and the amount rule catches a missing or changed number. | Amount and date only: this flags valid repeat bills. Exact invoice number only: this misses case and punctuation changes. | Invoice numbers are normalised on ingest. There are two exception types, `duplicate` and `possible_duplicate`. |
| D2 | tech | Ingest takes an idempotency key. A replay with the same key returns the first bill. Only a new submission can raise a duplicate exception. | **F2.** At-least-once clients must retry safely without false exceptions. | No key: a retry raises a false duplicate. Content hash as key: a real resubmission becomes invisible. | The bill table has a unique (tenant, idempotency key) pair. |
| D3 | product | Purchase order is a domain entity. A user ingests it the same way as a bill. PO sync from accounting software is not in v1. | **F3.** The PO-mismatch check needs PO data, and manual ingest is the smallest source. | Sync POs from Xero: this adds a second adapter flow before v1. Remove the PO check: this removes one of the three core checks. | The domain has a PO entity. A bill can reference a PO number. |
| D4 | tech | Enqueue uses a transactional outbox with a relay. A sweeper re-enqueues a job that stays `queued` past a limit. | **F4.** The job row and the enqueue intent commit in one transaction, so a crash cannot separate them. | `on_commit` only: a crash after commit loses the enqueue. Enqueue before commit: a worker can run for a row that rolled back. | There is an outbox table and a relay process. Handlers are idempotent because the relay can send twice. |
| D5 | tech | An exception is unique on (bill, rule, fingerprint). A check upserts it. A re-check does not reopen an `ignored` exception. | **F5.** Concurrent or repeated checks must give one exception for one problem. | Insert each time: this double counts. A lock per bill: this serialises checks and still needs dedup on retry. | There is a unique constraint on the exception. Each rule defines its fingerprint. |
| D6 | product | A re-check that no longer finds an open exception auto-resolves it, with `resolved_by = system`. | **F6.** The inbox must show only current problems. | Leave it open: the inbox fills with stale items. Delete it: the history is lost. | An exception records who resolved it: a user or the system. |
| D7 | tech | A proposal stores the versions of the bills and exceptions it read. Approve fails if a version changed. The user must request a new proposal. | **F7.** Optimistic concurrency stops a plan made for old data from being applied. | Re-validate the plan on approve: the plan logic runs twice. No check: a stale plan moves money. | Bills and exceptions have a version column. A proposal can become `stale`. |
| D8 | tech | Approve is a conditional update from `pending` to `approved`. Each apply action has a stable idempotency key that goes to the adapter. | **F8.** Only one approve can win. A repeat apply delivery must not post twice to accounting. | A row lock on approve: this gives the same result with more contention. No adapter key: a retry duplicates the credit or hold in Xero. | `AccountingSyncPort` takes an idempotency key. The stub adapter records keys and enforces them. |
| D9 | tech | The apply states are `approved → syncing → synced \| sync_failed`. The worker retries 5 times with backoff. After that, a user can retry manually. | **F9.** A stuck approved proposal must become a visible state. The approve stays committed. | Retry without limit: a hard failure never shows. Roll back the approve: this breaks the brief rule that a failed sync does not undo an approve. | The console shows `sync_failed` items and a retry action. |
| D10 | product | An exception becomes `resolved` on sync success. Between approve and sync it is `pending_sync`. | **F10.** Money is not safe until accounting has the action. | Resolve on approve: the report hides money that has not synced. | The exception statuses are `open`, `pending_sync`, `resolved` and `ignored`. |
| D11 | product | There are two roles, `clerk` and `approver`. An approver cannot approve a proposal they requested. | **F11.** Four-eyes control stops one user from controlling the full path to moving money. | One role: one user controls everything. A configurable rule per tenant: this adds settings that v1 does not need. | A tenant needs at least two users to complete an apply. The audit row stores the requester and the approver. |
| D12 | tech | Tenant isolation uses a tenant-scoped manager and Postgres row-level security. Each task carries `tenant_id` and sets the session tenant first. | **F12.** Two layers: one missing filter in code does not leak rows. | Manager only: one raw query leaks rows. Schema per tenant: migrations and pooling cost more. | Each table has a policy on `tenant_id`. Each worker task sets the session variable before it reads. |
| D13 | product | Money at risk sums each bill with an open exception once, grouped by currency, in minor units. | **F13.** A bill is at risk once, whatever its exception count, and currencies do not add. | Sum per exception: this double counts. Convert to one currency: this needs FX rates, which v1 does not have. | The report shows one total for each currency. |
| D14 | tech | Money is an integer in minor units with an ISO 4217 currency code. Floats are never used. | **F14.** Integers give exact sums. | Decimal column: this is exact but makes currency precision less clear. Float: this gives rounding errors. | Each money field has an amount and a currency. |
| D15 | tech | One user belongs to one tenant. The tenant comes from a JWT claim. It never comes from a request argument. | **F15.** The server must set the tenant from a trusted source. | A tenant argument: a user can ask for another tenant. Users in many tenants: this adds a switch flow that v1 does not need. | The OIDC mapping must put the tenant id into the token. |
| D16 | tech | Each bill in a batch gets its own result. A failed bill does not fail the batch. The job is `completed` with a count of failed bills. | **F16.** One bad bill must not block the others. | Fail the batch: one bill blocks all. | The job row stores a count of failed bills. A bill can be `check_failed`. |
| D17 | tech | A message that fails 3 times goes to a dead-letter queue and marks its bill `check_failed`. | **F17.** A poison message must stop and become visible. | Retry without limit: the poison message blocks the queue. Drop it: the failure is lost. | Each queue has a dead-letter queue. |
| D18 | tech | Postgres holds the job state. Redis progress is a cache. On WebSocket reconnect, the console reads the job row first. | **F18.** Redis can lose data, so it cannot be the truth. | Redis as the truth: a restart loses the state. Postgres for each tick: this writes too often. | The job row stores the status. Redis stores only the percentage. |
| D19 | tech | Each progress event carries a sequence number. The console drops an event older than the last one it showed. | **F19.** Delivery order is not guaranteed. | Trust delivery order: the progress can go back. | The event schema has a `seq` field. |
| D20 | tech | The agent loop runs max 8 tool calls and max 60 s. Then the proposal is `failed`. | **F20.** A bounded loop protects the quota and the queue. | No bound: one run can use the full quota. | A proposal can be `failed`, and it stores the reason. |
| D21 | product | The proposal quota counts requests per tenant per day. | **F21.** A request count is simple to show and to enforce. | Count tokens: this is more exact but harder to show to a user. | Over the quota, the request returns 429. |
| D22 | tech | A supplier is unique per tenant on its normalised VAT number, or else on its normalised name. | **F22.** One supplier must have one record, or duplicate checks miss bills. | Name only: two suppliers with the same name merge. No rule: the same supplier exists twice. | Ingest matches a supplier before it creates a new one. |
| D23 | tech | A webhook or sync callback must have a valid signature. Without one, the server returns 401 and writes nothing. | **F23.** Callbacks change sync state, so they must be authenticated. | No check: a forged callback can mark an apply as synced. IP allowlist: this breaks when provider addresses change. | Each adapter verifies its provider's signature. |

## 2026-10-21 — user stories in `domain.md`

| # | Kind | Decision | Why | Alternatives considered | Consequence |
|---|---|---|---|---|---|
| D24 | product | Supplier name matching keeps legal suffixes. "Green Co" and "Green Co Ltd" are two suppliers. | VAT is the main match key (D22). A false merge raises false duplicates across two real companies. | Remove suffixes: two companies merge, and their bills raise false duplicate exceptions. | A supplier with no VAT can exist twice under two suffixes. A user sees both in the supplier list. |
| D25 | product | A receipt is a yes/no field on the bill. | The `missing_receipt` rule needs only "exists or not". | File upload: this needs storage and file scanning, which v1 does not need. Goods-received reference: this needs a second document type. | The bill has a `has_receipt` field. |
| D26 | tech | An idempotency key that comes again with a different payload returns 422. Nothing is stored. | A changed payload is a client defect. Returning the first bill hides a bill that nobody then checks. This follows the IETF Idempotency-Key draft. | Return the first bill: the second bill is lost without a signal. | Ingest stores a hash of the payload with the key. |
| D27 | product | Severity: `duplicate` and `po_mismatch` high, `possible_duplicate` and `missing_vat` medium, `missing_receipt` low. | A duplicate or a PO mismatch pays the wrong money. The others are a tax or paper risk. | Severity per tenant: this adds settings that v1 does not need. | Each rule has one fixed severity. |
| D28 | product | No `missing_po` rule in v1. A bill with no PO number gets no PO check. | Many SME bills have no PO, such as utilities. A rule would fill the inbox. | A `missing_po` rule: the inbox fills with expected items. | The check has 5 rules. |
| D29 | product | `ignored` is a final status in v1. | A reopen adds a state path and an audit case for a rare need. | A reopen action: more transitions to guard. | To undo an ignore, a later version adds a reopen story. |
| D30 | product | Proposal quota is 50 requests per tenant per day. Rate limit is 5 requests per tenant per minute. A 429 does not count. | 50 covers a busy SME day. 5 per minute stops a click loop. | No rate limit: a loop uses the day's quota in seconds. | Both limits return 429. |
| D31 | product | `hold` stops payment in accounting. `credit` asks the supplier for a credit note. `match` links the bill to a PO in accounting. No action changes a stored bill. | Bills are durable facts (brief). Accounting holds the payment state. | Actions change our bill too: a second copy of the payment state. | A bill does not change after ingest, except its check status. |
| D32 | product | Only an approver can retry a failed sync. | A retry sends money actions. The four-eyes control (D11) must cover it. | A clerk can retry: a clerk can re-send an action without an approver. | The retry command checks the `approver` role. |
| D33 | product | The signed sync callback is in v1. | D23 needs a test target, and the Xero adapter needs callbacks. | Remove it: the REST edge in the brief has no callback route. | The stub adapter can also send a callback in tests. |

## 2026-10-21 — invariants and contexts in `domain.md`

| # | Kind | Decision | Why | Alternatives considered | Consequence |
|---|---|---|---|---|---|
| D34 | tech | Payables is one context. It owns suppliers, POs, bills, check jobs, exceptions, resolutions and proposals. Identity and Accounting are outside systems. Reporting is a read model. | Accounts payable is one department. The approve must claim exceptions in the same context, or the use case changes another context's aggregate. | Seven contexts from the story groups: the approve crosses a boundary in one transaction. A saga across contexts: it adds a `claiming` state and an undo path. | Each worker queue is a deployment unit inside Payables. No context arrow runs inside a transaction. |
| D35 | tech | An exception has at most one resolution row: ignore, system resolve or approved proposal. The approve writes the rows in its transaction. A unique key on exception id guards it. A conflict makes the proposal `stale`. | Approve vs approve, approve vs ignore and approve vs re-check all race on one exception. One key stops all three. | A status on the exception changed by the approve: the approve changes N other rows under N versions. A saga: see D34. | D7 keeps its rule: a stale plan never applies. The unique key enforces it, so bills and exceptions need no version column. A re-check that finds a system-resolved problem again deletes that resolution. |
| D36 | tech | The quota uses slots. Each proposal takes a slot from 1 to 50, unique per tenant and day. | A separate counter row makes the request change two aggregates. | A counter row with a conditional increment: two aggregates in one transaction. Redis counter: a restart loses the count. | On a unique conflict, the request takes the next slot. Slot 51 does not exist, so the request returns 429. |
| D37 | tech | A check result is a row per job and bill, in the job aggregate. The bill does not change. | D31 says a bill does not change after ingest. A status on the bill makes the check worker change the bill. | `check_failed` on the bill: the bill changes, and two jobs on one bill overwrite each other. | The job root holds its check results. A row lock on the job guards completion (I13). |
| D38 | tech | Exception status, job failed count and money at risk are derived on read. | Stored copies need an invariant only to keep them in agreement. | Store the status and update it by event: a lag and one more handler. | The exception table has no status column. The queries join the resolution and the proposal. |
| D39 | tech | The apply needs no saga. The proposal aggregate records each action's status. The `ApplyFixProposal` command starts the apply. | Each step changes one aggregate, the proposal. A saga is needed only when a step changes a second aggregate or context. | A process manager for the apply: one more state machine with no new rule to guard. | The apply handler and the callback route both change only the proposal. |

## 2026-10-21 — aggregates, events and eventual strategy in `domain.md`

| # | Kind | Decision | Why | Alternatives considered | Consequence |
|---|---|---|---|---|---|
| D40 | tech | The proposal aggregate uses a row lock on the root for each change. Approve is a conditional update from `pending`. | Callbacks for two actions can arrive at once (I11). A lock is simple and the contention is per proposal. | Version number on the proposal: a callback that loses must retry, and callbacks come from outside. | Each proposal write starts with `SELECT … FOR UPDATE` on `proposal`. |
| D41 | product | A check job is `failed` only when every bill in it failed. Else it is `completed` with a failed count. | D16 says one bad bill does not fail the job. A job with no good bill gave the clerk nothing. | `failed` never used: the brief's state list then has a dead state. | The job board shows `failed` only for a job with no result. |
| D42 | tech | No inbox table. Each handler is idempotent by a key it already has: I6, the check result PK, the status condition, the sync key. | An inbox adds a table and a cleanup cron for dedup that the keys already give. | Inbox table per handler: one more write per message, and a delete age to manage. | A new handler must name its own idempotency key, or add an inbox. |
| D43 | tech | Broker: at least once delivery. Durable queues, persistent messages, no TTL. Each queue has a DLQ. The owner replays the DLQ within 3 days. Outbox rows are deleted 7 days after `sent_at`. | At least once is the RabbitMQ default with publisher confirms. Handlers are idempotent (D42). 7 days covers the 3-day replay window with margin. | Message TTL: a worker down past the TTL loses commands. Delete outbox rows at once: no record to replay from. | The owner is the operator of this deploy. A runbook entry covers the DLQ replay. Celery sets `acks_late=True` and `task_reject_on_worker_lost=True`, because its default acks before the task runs, which is at-most-once. The relay uses publisher confirms and sets `sent_at` after the confirm. |
| D44 | tech | I16 uses an in-process handler on `PurchaseOrderAdded`. It starts a check job for bills with an `open` `po_mismatch` on that PO number. | Only a new PO can make an open exception stale, because bills and POs do not change. | Cron re-check of all open exceptions: work every night for a rare case. Manual re-check only: a fixed problem stays in the inbox. | Adding a PO can start a check job that no user started. The job's `requested_by` is `system`. |
| D45 | tech | Messages are a mix. User intents and worker tasks are commands with one handler: `CheckBill`, `DraftFixProposal`, `ApplyFixProposal`. Facts are events: `PurchaseOrderAdded` through the outbox; progress and status changes to the console. | A Celery task goes to one queue and one handler, so it is a command. The brief names commands and events the same way. | All events: a task named as a fact hides that exactly one handler must do it. All commands: the PO use case then calls the check, and must know about it. | Command names are imperative. Event names are past tense. The relay sends commands to their queue. |
